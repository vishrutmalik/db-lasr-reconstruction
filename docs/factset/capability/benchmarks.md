## 1. API identity, transport, authentication

All `DOCUMENTED_OPENAPI` unless tagged otherwise.

- Title: **FactSet Benchmarks API**, version **1.11.0**, OpenAPI 3.0.0. Vendor
  description: "gives access to Index Constituents, Prices, Returns, and
  Ratios … Equity Only - Fixed Income Benchmark support coming soon." (That
  sentence contradicts the spec's own two fixed-income operations, and the
  description's pointer to a "/metrics endpoint" names an endpoint that does not
  exist in this API — both recorded as `BM-DISC-03`.)
- Server: `https://api.factset.com/content` (single production server). All
  paths are prefixed `/factset-benchmarks/v1/`.
- Security: the spec declares **only `BasicAuth`** (HTTP basic;
  username = USERNAME-SERIAL, password = API key, IP-range-restricted per the
  401 text). The SDK documents **both** FactSetApiKey and FactSetOAuth2, and the
  vendor demo authenticates via OAuth2 `ConfidentialClient` — the spec omits the
  OAuth2 scheme that every sibling family spec declares (`BM-DISC-01`;
  operationally OAuth2 is expected to work platform-wide, but that is
  `DOCUMENTED_SDK`, not spec-documented).
- Content type: `application/json` only (415 otherwise). No CSV arm exists in
  this family (unlike Global Prices batch results).
- Request-line limit: GET URLs limited to **8,192 bytes**; vendor advises POST
  for large id lists (stated in the `indexIds` and `metrics` descriptions).
- Read timeout: 400 "The request took too long. Try again with a smaller
  request." if the backend takes **more than 29 seconds**. Note: for
  `/constituents` there is no way to "try a smaller request" — one id, one date,
  no pagination — so very large snapshots (S&P Global BMI ≈ 14k rows) are a
  retry-only risk (`BM-UNRES-15`).
- Rate limits: **none documented anywhere in the spec or SDK README**
  (`BM-UNRES-07`; FS010 must impose conservative client-side limits).

### 3.2 Identifier-join verdict (binds to FS003 Symbology manifest)

The constituent payload carries **no CUSIP, SEDOL, ISIN, or ticker** — only
FactSet permanent identifiers at security (`-S`) and regional (`-R`) level, plus
cash/generic passthroughs (`CASH_USD`). Join mechanics:

1. **Direct fsym joins (no translation needed):** Global Prices accepts FactSet
   Permanent IDs as inputs and keys responses on `-R`/`-L`/`-S` fsyms;
   Fundamentals likewise. The fsym spine is the natural join.
2. **Symbology translation:** `fsymSecurityId` and `fsymRegionalId` are valid
   `inputSymbolType` values in both Symbology resolution operations (FS003 §3.1,
   31-value enum / §3.2, 28-value enum). Historical resolution outputs are
   **SEDOL/CUSIP/ISIN/tickerRegion only** (FS003 finding), each with validity
   intervals — so benchmark membership CAN be translated to exchange identifiers
   historically, with the caveat that SEDOL/CUSIP/ISIN output types are
   subscription-gated (FS003 U-1) and one-to-many fan-out handling is
   unresolved on the Symbology side (FS003 register).
3. **Cash/generic rows must be filtered before any join** (documented
   passthrough behavior) — an adapter-level typed rule for FS016.
4. `INFERRED`: `-S` is the level to use for fundamentals joins and `-R` for
   pricing joins, mirroring the Global Prices response-key conventions (its CA
   and dividend series key on `-R`, shares on `-S`). Verify in FS016.

## 4. Constituent retrieval semantics — the reconstruction verdict (WP9 item 1)

All `DOCUMENTED_OPENAPI` (by exhaustion of the operation/parameter inventory):

- `/constituents` takes **one benchmark id** and **one optional `date`**
  (`YYYY-MM-DD`) and returns the full membership snapshot for that date in a
  single, unpaginated, synchronous 200.
- There is **no date-range parameter**, **no membership-interval endpoint**,
  **no add/drop (delta) endpoint**, and **no reconstitution-calendar endpoint**
  anywhere in this API.
- Future dates are rejected (400 "The use of future dates is not applicable in
  this endpoint"). Historical dates are accepted; **how deep history reaches is
  nowhere stated** (BM-UNRES-03), and whether a past-date snapshot is frozen as
  originally published or restated/backfilled is nowhere stated (BM-UNRES-02).
- Omitted `date` behavior is unstated (BM-UNRES-04; presumably latest —
  INFERRED, pin live). Non-trading-day dates: the FIVEDAY calendar "displays
  Monday through Friday, regardless of whether there were trading holidays",
  i.e. values repeat on holidays (documented for display; exact snap-back rule
  for constituents unstated, BM-UNRES-04).

**Verdict: historical membership MUST be reconstructed from repeated
single-date snapshots — exactly what WP9 anticipated.** What the spec supports
is precisely: one (benchmark, date) → one full snapshot. Consequences for the
FS016 pull design:

1. Pull cost is one request per (benchmark, date): monthly 2010–2025 for the
   principal benchmark ≈ **192 snapshots**; quarterly for each secondary ≈
   **64**; plus reconstitution-window extras. Russell 3000 ≈ 3,000 rows/snapshot;
   S&P Global BMI ≈ 14,000 rows/snapshot (29s-timeout sizing risk, BM-UNRES-15).
2. Reconstitution dates themselves are **not servable from this API** — the
   extra-snapshot schedule needs an external calendar (Russell June
   reconstitution, S&P quarterly effective dates) (BM-UNRES-09).
3. `INFERRED` strategy from documented fields: `/index-history` at
   `frequency=D` serves a **daily `constituentNumber` series** — count changes
   locate membership-change dates cheaply (500 ids per request, long ranges),
   letting FS016 target additional snapshots without daily membership pulls.
   The count series cannot detect same-day one-in-one-out swaps (count
   unchanged) — it bounds, not replaces, snapshot density.
4. Snapshot cadence honesty — vendor observations vs inferred membership: the
   only thing the vendor DOCUMENTS is the dated snapshot observation
   (benchmark, date) → members. Any continuous membership interval built
   between two snapshots is an FS016-constructed INFERENCE, never vendor data,
   and the canonical membership table must keep the two ontologically
   separate: observed-snapshot rows (vendor-attributable) vs derived intervals
   (transformation-versioned), with interval closure justified only by a
   swap-free count series (FS016 design decision, flagged here).
5. Knowledge-time vs effective-date policy: the spec is SILENT on whether a
   past-date snapshot is served frozen-as-originally-published or
   retrospectively maintained (corrections, restatements, backfills) —
   BM-UNRES-02, VENDOR_CLARIFICATION_REQUIRED. Until resolved, a snapshot
   retrieved today for e.g. 2015-06-30 carries knowledge-time = retrieval
   date and effective-date = 2015-06-30, and must NOT be graded as
   known-at-2015 (PIT) without the BM-UNRES-02 answer or a WP9 probe result.

## 5. Index-level series (WP9 item 3)

All `DOCUMENTED_OPENAPI`.

### 5.1 Levels and returns — TR distinct from PR: YES

- **Price level**: `price` ("Index Level Price") + `priceReturnPercent`
  (history) / `priceReturnPercent1D|QTD|YTD` (snapshot).
- **Total-return level**: `totalReturnLevel` ("Index Level Total Return Amount.
  (Gross or Net depends on requested returnType)") + `totalReturnPercent`
  variants. The WP9 requirement that index TR be distinct from PR is satisfied
  at the documentation level: separate level fields, separate percent fields.
- **`returnType`**: `GROSS` (default) | `NET` — "Adjustment can be made for
  GROSS and NET dividends that will be included in the return calculation."
  One arm per request → gross AND net TR require two calls. NET withholding
  methodology is not referenced anywhere (BM-UNRES-11).
- **`hedgeType`**: `UNHEDGED` (default) | `HEDGED` — on **index-history and
  index-returns only**; `/index-snapshot` has no hedge lever (asymmetry, so
  snapshot TR is implicitly unhedged — INFERRED). Hedging methodology
  undocumented (BM-UNRES-11).
- **Market cap**: `marketValue` — index-level market capitalization "expressed
  in millions". **Historical index market cap IS servable** via index-history
  (unlike Global Prices' current-only `/market-value`).
- `constituentNumber` — total constituents as of each observation (snapshot +
  history), the WP9 count field and the §4 change-detector.
- `inceptionDate` — index inception (NOT data-history depth; BM-UNRES-03).
- Percent-change units: documented "percent change"; examples consistent with
  percent (CY2019 S&P 500: `priceReturnPercent: 28.878…`,
  `totalReturnPercent: 31.486…`). Period basis of `priceReturnPercent`/
  `totalReturnPercent` in history = per displayed frequency period (INFERRED
  from the CY example; not stated — BM-UNRES-10).

### 5.2 The three retrieval shapes

| Endpoint | Shape | Date lever |
|---|---|---|
| `/index-snapshot` | one row per id: levels + 1D/QTD/YTD percent | single optional `date` |
| `/index-history` | time series per id at `frequency` | optional startDate/endDate (both-omitted behavior unstated, BM-UNRES-04) |
| `/index-returns` | ONE cumulative `totalReturnPercent` per id per window ("does not return a time series or support frequency parameters") | required startDate + endDate |

`/index-returns` caveats: its documented formula "((startDate level / endDate
level) - 1) * 100" is **inverted**, and its example value matches neither that
formula nor the corrected one (BM-DISC-05) — FS016 must pin the actual
convention live before using it even as a cross-check. Its response also has no
date field, making the `impliedDate` parameter inert there (BM-DISC-12). The
documented good part: "Dates are inclusive and based on closing levels;
non-trading days use the nearest available trading date."

### 5.3 Calendar and date-labeling semantics

- `calendar` (regionCalendar, free string, default `FIVEDAY`): FIVEDAY
  "displays Monday through Friday, regardless of whether there were trading
  holidays"; `SEVENDAY` adds weekends; region codes (e.g. `NAY` = US) per OA
  16610. Because non-trading days are displayed, **values repeat** on
  weekends/holidays.
- `impliedDate` (`N` default): `N` → the `date` field repeats the actual
  observation date on non-trading days; `Y` → implied unique dates.
  `indexHistory.observationDate` always carries the actual data date — the
  unambiguous anchor for joins; the adapter should key on `observationDate`,
  not `date` (INFERRED consequence).
- `frequency` enum (index-history, ratios): `D` daily, `W` weekly (last day of
  week of startDate), `M` monthly (last trading day), `AM` monthly anchored on
  startDate's day, `CQ` calendar quarterly (last trading day of Mar/Jun/Sep/
  Dec), `AY` actual annual (startDate-anchored), `CY` calendar annual. No
  AD/AQ/ASA/CSA arms (narrower than Global Prices' 11-value enum). GET default
  `D` vs POST-body default `CY` (BM-DISC-04) — always pass explicitly.

### 5.4 `/ratios` (FactSet Market Aggregates) — NON-PIT convenience

Index-level aggregated ratios: `metrics` (required, 1–38 per request; complete
documented list of exactly 38 metric codes across Profitability, Valuation,
Coverage, Leverage — full table in `benchmarks.json`), `periodicity`
(`LTM` default | `LTMA` | `STMA` | `NTMA` | `0` latest reported CY | `1` current
unreported | `2` following year | `QTR`; not all periodicities valid per metric
— per-metric matrix documented in the metrics table), plus startDate/endDate/
frequency/currency. "Using FactSet Market Aggregates, the service combines
fundamental, estimates, and pricing content … constituents of the index are
fetched on rolling basis over time period requested."

PIT posture (project law): FMA mixes **estimates** content (NTMA/STMA/LTMA
arms) with fundamentals; no vintage/as-of statements exist (BM-UNRES-14).
Treat `/ratios` as NON-PIT-labeled index-level convenience — never a model
input without PIT grading; usable for descriptive context in the notebook.

## 7. Entitlement mechanics and error architecture (WP9 item 4, failure shapes)

All `DOCUMENTED_OPENAPI`. The entitlement TABLE (accessible / unauthorized / no
historical constituents / index-level only / complete enough / additional
licence) is **FS016's deliverable**; what the spec gives it:

- **Per-id entitlement is real**: constituents descriptions state "You must be
  authorized for the `ids` requested, otherwise you will receive an error."
  403 description covers the **endpoint** level; the 403 example body covers
  the **id** level: `{status: "Forbidden", message: "User is not authorized for
  the id requested, please reach out to FactSet for support"}`.
- **Invalid id vs unentitled id are indistinguishable** from documented bodies:
  the 400-example named "Bad Request - Passing invalid Benchmark Identifier"
  carries the SAME Forbidden body as the 403 case (BM-DISC-06). FS016 must
  therefore classify by cross-checking /id-list presence + multi-id triangulation
  (an id that 403s for this account but appears in /id-list ⇒ unentitled;
  absent from /id-list ⇒ ambiguous, needs vendor confirmation).
- Single error shape everywhere, `errorResponse`: `{status, timestamp, path,
  message, subErrors{object, field, message, rejectedValue[]}}` (subErrors null
  in every example).
- Documented 400 causes (7 examples): date format; missing required parameter;
  **future date**; invalid benchmark identifier (body says Forbidden);
  **more than one benchmark identifier** on constituents; malformed JSON; read
  timeout > 29s.
- 401: "User Authentication Failed" (USERNAME-SERIAL / API key / IP range).
- 415: only `application/json` accepted.
- 500: "Error writing JSON output" / "Unexpected error".
- No per-row inline errors exist in this family (closed response models) —
  id-level failures surface as whole-request 403s (single-id requests make
  this clean for constituents; for 500-id index requests, whether one bad id
  fails the whole request is unstated — fold into BM-UNRES-01 probing).

## 13. Historical-membership verdict (summary for FS016)

The spec supports exactly one retrieval shape for membership: **one benchmark ×
one date → full constituent snapshot** (synchronous, unpaginated, fsym-keyed,
with close weights, adj/unadj holdings, price, adjusted market value). It
supports **no** membership ranges, intervals, deltas, or reconstitution
calendars, so panel-grade historical membership must be **reconstructed from
repeated single-date snapshots** (monthly principal / quarterly secondary +
externally-sourced reconstitution dates), with `/index-history`'s daily
`constituentNumber` series as a cheap change-detector between snapshots.
The spec documents ONLY dated snapshot observations; any continuous membership
series is an FS016-constructed inference and must be labeled as such, never as
vendor data. The spec says NOTHING about whether past-date snapshots are
frozen-as-published or retrospectively maintained (BM-UNRES-02,
VENDOR_CLARIFICATION_REQUIRED) — until answered, reconstructed membership
carries knowledge-time = retrieval time and effective-date = snapshot date and
cannot be graded point-in-time; that answer plus history depth (BM-UNRES-03)
are the two live-probe gates on which the WP9 survivorship validation stands.
