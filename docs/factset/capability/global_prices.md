## 1. API identity, transport, authentication

All `DOCUMENTED_OPENAPI` unless tagged otherwise.

- Title: **FactSet Global Prices API**, version **1.12.0**, OpenAPI 3.0.0.
  Scope per vendor description: "end of day market pricing content … encompassing
  both pricing as well as corporate actions and events data."
- Server: `https://api.factset.com/content` (single production server). All paths
  are prefixed `/factset-global-prices/v1/`.
- External docs: `https://developer.factset.com/api-catalog/factset-global-prices-api`.
- Security (either scheme, declared globally for all operations):
  - `FactSetApiKey` — HTTP **basic** auth; error text establishes the username is
    the `USERNAME-SERIAL` and password the generated API key, with an **IP-range
    restriction** on the key (401 description).
  - `FactSetOAuth2` — OAuth2 **client-credentials** flow, token URL
    `https://auth.factset.com/as/token.oauth2`, no scopes.
- Content type: `application/json` only (415 otherwise); batch-result can return
  **CSV** when requested with `Accept: text/csv`.
- Request-line limit: GET URLs limited to **8,192 bytes**; vendor advises POST
  for large ID lists (stated in every ids parameter description).
- Read timeout: request fails with 400 "Request Timed Out" if the backend takes
  **more than 29 seconds** (error-example text); remedy per vendor: smaller request.
- Rate limits: **none documented anywhere in the spec or SDK README**
  (`GP-UNRES-06`, UNRESOLVED — FS010 must impose conservative client-side limits).

### 2.2 Batch processing endpoints

| Path | Method / operationId | Responses |
|---|---|---|
| `/batch-status` | GET `getBatchStatus` (param `id`: uuid, required) | **201** created (+`Location: batch-result?id=…`), **202** not finished (examples cover `queued`, `executing`, and `failed`), 404 `batch404` |
| `/batch-result` | GET `getBatchData` (param `id`: uuid, required) | **200** `BatchResultResponse`, **202** not finished, 404 |

Async pattern (DOCUMENTED_OPENAPI):

1. Submit any §2.1 operation with `batch=Y` → HTTP **202** with
   `BatchStatusResponse{data:{id, status:"queued", startTime, endTime:null}}` and
   `Location` header. Batch supports **long-running requests up to 20 minutes**.
2. Poll `GET /batch-status?id=` → 202 while `queued`/`executing`; **201** when
   `status:"created"` with `Location` → batch-result. `BatchStatus.status` enum:
   `queued | executing | created | failed`. **A `failed` status is delivered under
   HTTP 202** (per the spec's response examples), with `error:{id, code, title}`
   (`BatchErrorObject`) — pollers must terminate on `status=="failed"`, not on
   HTTP code alone (INFERRED consequence of the documented examples).
3. `GET /batch-result?id=` → 200 with `BatchResultResponse.data` (required):
   array of `BatchResult` = `anyOf` **6** payload objects (`Price`, `Returns`,
   `CorporateAction`, `AnnualizedDividendsObject`, `SharesOutstandingResponseObject`,
   `MarketValueResponseObject`). CSV available via `Accept: text/csv`.
4. 404 semantics: "The Batch Request was not found. **It has probably expired.**"
   — a retention window exists but its length is **not documented**
   (`GP-UNRES-07`, UNRESOLVED).

Batch timestamps are **Eastern Time**, ISO-8601 (`BatchStatus` description).
Calendar endpoints (§2.3) have **no** batch arm.

## 3. Shared request-parameter semantics

All `DOCUMENTED_OPENAPI`.

### 3.1 Identifiers

Accepted input ID types everywhere: **Market Tickers, SEDOL, ISIN, CUSIP,
FactSet Permanent IDs**. Responses key on:

- `fsymId` — FactSet Permanent Identifier. Prices/Returns: `-R` (regional) or
  `-L` (listing) suffix; Corporate Actions & Annualized Dividends: **regional
  `-R`** ("security's best regional security data series per currency"; allocated
  once a SEDOL representing region/currency exists); Shares Outstanding &
  Market Value: **security-level** (`-S` examples). Nullable in most models.
- `requestId` — echo of the identifier used in the request (join key back to
  the caller's universe).
- Calendar models additionally return `identifier` (ticker-region, always
  returned) plus `exchangeCode`/`exchangeName`/`country`/`companyName`.

### 3.2 Dates and frequency

- `startDate`/`endDate`: `YYYY-MM-DD`. Prices/returns/shares: start must precede
  end; **future dates (T+1) rejected** (400 "Future Date"). Corporate-actions
  dates are event filters: the frequency between the dates "is always set to the
  'event' frequency"; **omitting both dates pulls ALL events per id**; **future
  dates ARE accepted** to retrieve declared events.
- `frequency` enum (prices, returns, shares; default **D**):
  `D` Daily; `AD` "Actual Daily"; `W` Weekly (last day of the week of the start
  date); `M` Monthly (last trading day of month); `AM` monthly anchored on the
  start date's day-of-month; `AQ` Actual Quarterly; `CQ` calendar quarterly
  (last trading day of Mar/Jun/Sep/Dec); `ASA` actual semi-annual; `CSA` calendar
  semi-annual; `AY` actual annual (start-date anchored); `CY` calendar annual
  (last trading day of calendar year). The D-vs-AD distinction is not defined
  beyond the names (`GP-UNRES-09`; INFERRED: D fills per the selected calendar,
  AD returns actual trade dates only — must be verified in FS013).
- `calendar` enum (prices and shares only; default **FIVEDAY**): `FIVEDAY`,
  `SEVENDAY` ("includes weekends"), `US`, `LOCAL`. Holiday semantics of US/LOCAL
  and the fill method for non-trading days are otherwise undocumented
  (`GP-UNRES-10`).
- Returns endpoints take `frequency` but **no calendar**; returns-range takes
  **neither** (single window aggregate).

### 3.3 Currency

`currency` (default **LOCAL**) — "Currency code for adjusting prices"; ISO codes
per FactSet OA page 1470. Response `currency` field reports the delivered
currency. FX source/timing for **price** conversion is undocumented
(`GP-UNRES-12`); for corporate-action amounts the spec documents conversion "to
the trading currency based on the exchange rate **as of the effective date**".
Unique currencies per request capped at 50 (§2.1).

### 3.4 Precision and fields

- `precision` (prices only): integer 1–16, default 16 — decimal places of price
  fields.
- Prices `fields` (`PricesFields`, maxItems 8): `price` (Closing Price),
  `priceOpen`, `priceHigh`, `priceLow`, `volume`, `turnover` (Total Trade Value
  for the Day), `tradeCount` (Number of Trades), `vwap`. Default = all fields;
  `fsymId`, `date`, `currency` always included. The GET parameter's default list
  additionally names `currency` as a ninth default element while the POST model
  caps `maxItems: 8` — spec-internal wobble, no operational impact
  (`GP-DISC-09`).
- `Price` and `CorporateAction` response models declare
  `additionalProperties: true` — columns appear dynamically per requested
  fields; a fixed-schema client must not assume a closed column set
  (load-bearing for the adapter's raw-schema validation).

## 4. ADJUSTMENT SEMANTICS (load-bearing) and D-013 basis mapping

### 4.1 What the spec says — exact meanings

`adjust` (prices only; **default `SPLIT`**), DOCUMENTED_OPENAPI, quoted meanings:

| Value | Vendor meaning (verbatim) |
|---|---|
| `SPLIT` | "Split ONLY Adjusted. This is used by default." |
| `SPLIT_SPINOFF` | "Splits and Spinoff Adjusted." |
| `DIV_SPIN_SPLITS` | "Dividend adjustments, Spinoff, and Splits combined." |
| `UNSPLIT` | "No Adjustments." |

So the API serves **four price bases**: unadjusted (`UNSPLIT`), split-adjusted
(default), split+spinoff-adjusted, and a total-return-style price folding
dividends+spinoffs+splits (`DIV_SPIN_SPLITS`). The spec does **not** enumerate
which corporate-action event-type codes fold into each arm: e.g. whether
stock distributions (DVS/DVSS/BNS/BNSS — which carry price `adjFactor`s) and
rights issues (DSR — carries `priceAdjFactor`) are folded under "SPLIT", under
"DIV", or not at all is **unstated** (`GP-UNRES-02`,
VENDOR_CLARIFICATION_REQUIRED — this is the single most load-bearing unknown for
FS013 reconciliation; the hand battery must difference `UNSPLIT` vs each arm
across known DVS/BNS/DSR events to establish the fold empirically).

Related documented adjustment facts:

- Corporate-action **amount fields come in explicit adjusted/unadjusted arms**:
  every `amt*Adj` is "adjusted for splits", every `amt*Unadj` is "not adjusted
  for splits" (§6.3). So dividend amounts are only ever split-adjusted or raw —
  never dividend-adjusted.
- `adjFactor` (splits/distributions): "Factor applied to adjust historical
  prices … A 2-for-1 split returns .50, the number you would multiply the stock
  price by to adjust for the split" — i.e. **multiplicative price factor < 1 for
  forward splits**, formulas on OA page 12619. `adjFactorCombined`: "Combined
  adjustment factor for all distribution events on that day" (same-day event
  composition is pre-combined by the vendor — directly comparable to the
  G020 F1 order-invariance ledger).
- `dividendsSpecFlag`: "Indicates a special price implications exists … Indicates
  whether an adjustment should be made to historical pricing." (flag that a
  special dividend is price-relevant).
- Shares outstanding: "At this time, **all values returned are split adjusted**"
  — there is **no unadjusted arm for shares** (`GP-UNRES-03`,
  VENDOR_CLARIFICATION_REQUIRED: whether history is restated to the current
  split basis — which would be a look-ahead if stamped as-of `date` — or to the
  as-of-date basis; determines whether shares can enter the PIT layer as
  RETRO_WINDOW or must be SNAPSHOT_STAMPED).
- Returns endpoints have their own dividend treatment via `dividendAdjust` (§5);
  they take **no** `adjust` parameter (split handling inside returns is implicit
  and undocumented; INFERRED: returns are computed split-consistently, to be
  verified in FS013).

### 4.2 Mapping onto D-013 / provider_contract.md basis conventions

Project law (docs/architecture/provider_contract.md): `CorporateActionBasis ∈
{UNADJUSTED, ADJUSTED, UNKNOWN}`; CT-15 — **ADJUSTED-basis price payloads are
REFUSED at canonical build** (factors would double-adjust); UNKNOWN follows
D-011/D-015 (downgrade path). The FS013 adapter must therefore declare:

| API request | Declared basis | Canonical-layer consequence |
|---|---|---|
| `adjust=UNSPLIT` | `UNADJUSTED` | **Accepted** (the only acceptable arm). Pair with explicit actions from `/corporate-actions` (unadjusted amount arms + `adjFactor`s) so the canonical layer computes its own factors. |
| `adjust=SPLIT` (the **default**), `SPLIT_SPINOFF`, `DIV_SPIN_SPLITS` | `ADJUSTED` | **Refused** by CT-15. Never let these arms reach canonical price frames; usable only in quarantined reconciliation fixtures (FS013 battery compares them against internally-adjusted UNSPLIT series). |

Consequences (INFERRED from documented behavior + project law, each item's
factual basis documented above):

1. **The vendor default is refuse-worthy.** Because `adjust` defaults to
   `SPLIT`, an adapter that omits the parameter ships ADJUSTED prices. The FS013
   adapter MUST always pass `adjust=UNSPLIT` explicitly and record it in the
   dataset manifest; the transport (FS010) should treat a prices request without
   an explicit `adjust` as a programming error.
2. **Total-return construction stays in-house.** `DIV_SPIN_SPLITS` prices and
   `/returns` `totalReturn` are vendor-computed conveniences; under D-013/CT-15
   they serve as **cross-checks only**, not canonical inputs. Price-return vs
   total-return separation in the project comes from UNSPLIT prices + explicit
   CA events (A-G020-04 ledger conventions, incl. dividend-per-post-split-share
   for same-ex-date stacks — the vendor's `adjFactorCombined` and per-event
   `amt*Adj/Unadj` arms provide exactly the inputs that ledger needs).
3. **Currency**: request `currency=LOCAL` for the canonical arm so no silent FX
   transformation enters the price series; FX conversion happens downstream
   where its source is controlled (the API's price-FX timing is undocumented,
   GP-UNRES-12).
4. **Shares outstanding cannot currently declare UNADJUSTED** (split-adjusted
   only). Until GP-UNRES-03 is resolved, shares from this API enter as
   SNAPSHOT_STAMPED or with basis=UNKNOWN → D-011/D-015 downgrade applies;
   `publicationDate` (documented field) is the usable knowledge-time anchor.
5. `RETRO_WINDOW` grading of UNSPLIT daily bars is compatible with D-011
   (prices publicly knowable at bar close) **provided** the basis check passes —
   which UNSPLIT satisfies by construction.

**Adjustment-semantics verdict:** the API fully supports the canonical-layer
requirement — a genuinely unadjusted price arm (`UNSPLIT`) plus a complete,
dated, per-event corporate-action stream with explicit adjusted/unadjusted
amount arms and multiplicative price factors — but only if the adapter overrides
the vendor's split-adjusted default and treats all vendor-adjusted arms
(including all `/returns` output) as reconciliation material, never canonical
input. The one materially open adjustment question is which event types fold
into each `adjust` arm (GP-UNRES-02) and the restatement basis of shares
outstanding (GP-UNRES-03).

## 5. Returns endpoints — documented vs silent conventions

DOCUMENTED_OPENAPI:

- `/returns` (per-period series at `frequency`) and `/returns-range` (single
  aggregate over a mandatory startDate–endDate window; "total calculated
  returns"). Output models `Returns` / `ReturnsRange`: `fsymId`, `totalReturn`
  (number, double), `date` (returns only; "End date of the return … could
  represent the entire return period requested"), `currency`, `requestId`.
- `dividendAdjust` enum (default **EXDATE_C**) — the *only* documented lever on
  return computation:
  - `PRICE` = "Price Change - Dividends Excluded." (price return)
  - `EXDATE` = "Simple Return - Dividends Received on exdate but not reinvested."
  - `PAYDATE` = "Simple Return - Dividends Received on paydate but not reinvested."
  - `EXDATE_C` = "Compound Return - Dividends reinvested on exdate." (default)
  - `PAYDATE_C` = "Compound Return - Dividends reinvested on paydate."
  So the API distinguishes price return, simple (unreinvested) total return, and
  compound (reinvested) total return, with ex-date vs pay-date dividend timing —
  a genuinely richer convention menu than most vendors document.

Silent (all UNRESOLVED unless noted):

- **Units and orientation of `totalReturn`** (`GP-UNRES-01`): percent vs
  decimal fraction is nowhere stated; the only evidence is examples
  (`0.927077`, `1.782245` for a single dated observation), plausible as daily
  percent but not provable offline. Also unstated: whether a frequency-sampled
  series reports per-period returns or cumulative-from-start. FS013 must pin
  this with a hand-computable live case before any use.
- Split handling inside returns: implicit (no `adjust` parameter) — INFERRED
  split-consistent, verify in FS013.
- Gross vs net dividends in return computation (the CA endpoints distinguish
  net/gross amounts; returns do not say which is used) — `GP-UNRES-15`,
  VENDOR_CLARIFICATION_REQUIRED (materially changes TR for withholding-tax
  markets; interacts with `taxRate`).
- Currency-return composition (is FX applied to the price path or to the
  return?) — silent; part of GP-UNRES-14.
- No calendar parameter: period boundary behavior on holidays is silent.

| Category (`eventCategory`) | Event type codes |
|---|---|
| `CASH_DIVS` Cash Dividends | `DVC` Dividend; `DVCD` Dividend with DRP Option; `DRP` Dividend Reinvestment |
| `STOCK_DIST` Stock Distributions | `DVS` Stock Dividend; `DVSS` Stock Dividend, Special; `BNS` Bonus Issue; `BNSS` Bonus Issue, Special |
| `SPINOFFS` | `SPO` Spin Off |
| `RIGHTS` | `DSR` Rights Issue |
| `SPLITS` | `FSP` Forward Split; `RSP` Reverse Split; `SPL` Split; `EXOS` Exchange of Securities |

`ALL` (default) returns everything. **Mergers/acquisitions, delistings, ticker
changes and other capital events are NOT in the documented taxonomy**; `EXOS`
(exchange of securities) is the nearest documented type and is itself
inconsistently carried: the `CorporateAction.eventTypeCode` possible-values list
omits EXOS (lists only 12 codes) and the calendar `SplitCalendar.eventTypeCode`
enum is only `FSP|RSP|SPL`, though both endpoint descriptions include EXOS
(`GP-DISC-10`, spec-internal inconsistency; resolve empirically in FS013).

### 6.2 Date fields (per event, all `YYYY-MM-DD`)

- `announcementDate` — "Date Event was publicly announced" (nullable; several
  spec examples show `null` announcements — announcement coverage is not
  guaranteed; knowledge-time anchoring on announcementDate alone is unsafe,
  INFERRED from documented nullability).
- `recordDate` — record date of the distribution.
- `payDate` — payment date.
- `effectiveDate` — "Effective Date or **Ex-Date** of distribution" (the
  ex-date; this is the price-relevant date; always included in responses).
- Filtering by startDate/endDate is on events within inclusive boundaries
  ("event frequency"); **future dates return declared events** — the API is
  forward-looking for declared corporate actions (usable for pending-event
  awareness; must NOT leak into backtests, INFERRED caution).
- No "knowledge/entry timestamp" (when FactSet learned of the event) is
  documented anywhere — PIT grading of CA data must follow snapshot rules
  (`GP-UNRES-13`).

### 6.3 Field dictionary (`/corporate-actions` `fields`, maxItems 36)

Always included: `fsymId`, `effectiveDate`, `eventTypeCode`, `requestId`.
Common: `eventId`, `eventTypeDesc`, `divTypeCode` (OA#8764), `announcementDate`,
`recordDate`, `payDate`.

Dividend fields: `currency` (trading currency of the record);
`amtDefNetGrossIndicator` (G=Gross, N=Net — declares which arm `amtDef*` is);
default/net/gross × trading/declared × adjusted/unadjusted amount matrix —
`amtDefTradingAdj`, `amtDefTradingUnadj`, `amtNetTradingAdj`,
`amtNetTradingUnadj`, `amtGrossTradingAdj`, `amtGrossTradingUnadj`,
`declaredCurrency`, `amtDefDecAdj`, `amtDefDecUnadj`, `amtNetDecAdj`,
`amtNetDecUnadj`, `amtGrossDecAdj`, `amtGrossDecUnadj` (trading-currency amounts
translated at the **effective-date FX rate**; `*Adj` = split-adjusted, `*Unadj`
= raw); `dividendStatus` (Active / Cancelled / Postponed / Partial Information;
DVC+DVCD only); `dividendActiveFlag` (1/0; DVC+DVCD only); `dividendsSpecFlag`
(special price implications); `dividendFrequencyDesc` / `dividendFrequencyCode`
(OA#8764); Australian franking block `frankDefTradingAdj/Unadj`,
`frankDefDecAdj/Unadj`, `frankPct`; `taxRate` (domestic withholding rate for a
resident individual).

Distribution fields: `adjFactor`, `adjFactorCombined` (§4.1), `distPct`
(distribution %), `distOldTerm`/`distNewTerm` (ratio: shares held → shares
received), `rightsIssuePrice`, `rightsIssueCurrency`, `shortDesc`.

Splits fields: `adjFactor`, `adjFactorCombined`, `distOldTerm`, `distNewTerm`,
`distInstFsymId` (instrument of the distributed company/security — documented
for BNS, DVS, DSR, SPO), `shortDesc`. (Note: the Splits-section description of
`adjFactor` is a copy-paste of the distribution-percentage text; the Split
model's own definition — multiplicative factor, 2-for-1 → 0.50 — governs.
`GP-DISC-11`, spec-internal.)

`cancelledDividend` request parameter: `include|exclude` (default **exclude**) —
cancelled dividends are invisible unless asked for; with `include`, status is
readable via `dividendStatus`/`dividendActiveFlag`. FS013's battery should run
`include` and reconcile against price factors (cancelled events must not
adjust).

### 6.4 Identifier continuity across events

- `eventId` — "FactSet Event Identifier - a unique identifier for an event
  **across multiple exchanges**" (calendar) / "uniquely identifies the Event"
  (core). Spec example shows the same `eventId` (`NQTVZK-A`) returned for two
  different `fsymId`s (Nestlé's CH and US lines) — event identity is shared
  across listings, the per-listing rows differ in trading-currency amounts.
  `-A` suffix convention is unexplained (INFERRED: event-namespace fsym).
- `fsymId` regional (`-R`) keys the security line; `distInstFsymId` (core) /
  `distIdentifier` (calendar) key the **distributed** instrument for
  BNS/DVS/DSR/SPO — the spin-off continuity hook (parent → child instrument).
- Calendar `detailsRelativePath` points to
  `/content/**corporate-actions/v1**/dividends?...` — a **different API family**
  than this spec (`GP-DISC-12`; entitlement implications unknown, part of
  GP-UNRES-08).

### 6.5 Annualized dividends

`/annualized-dividends` (GET/POST): latest reported dividend annualized
(`iadDefTradingAdj`, split-adjusted, trading currency), `effectiveDate`,
`eventId`, `currency`. "The annualized dividend calculations does not involve
cancelled dividends." Current-state convenience — not a historical series
(no date-range parameters).

### 6.6 Calendar-detail models

Calendar responses (per §2.3) return per-event rows with company/exchange
context (identifier, companyName, exchangeCode/Name, country), the four date
fields, and type-specific payloads: dividends — `dividendType`,
`dividendStatus`, `dividendPerShare` (declared currency), `declaredCurrency`;
stock-distributions / rights-issues / spin-offs / splits — `priceAdjFactor`
(named `adjFactor` in the core endpoint), rights add `rightsIssuePrice`/
`rightsIssueCurrency`, splits add `distOldTerm`/`distNewTerm`; all carry
`eventDescription` and `distIdentifier` where applicable. **Per-row inline
errors**: calendar rows may be `{requestId, error:{code,title,detail}}` (e.g.
`notFound` "There's no data for this id", `parameterError` "This is not a valid
id") — data and per-id failures are mixed in one array (adapter must split them;
maps onto the project's typed-refusal rules, INFERRED consequence).

## 7. Shares outstanding and market value

DOCUMENTED_OPENAPI:

- `/security-shares`: security-level shares outstanding time series (frequency +
  calendar sampling). **Split-adjusted only** (§4.1). Fields:
  `fsymId` (security `-S`), `date`, `documentId` (source filing/document id),
  `reportDate` (position's reporting date), `publicationDate` ("Exact date that
  results have been communicated to the market" — the PIT anchor),
  `fiscalYear`, `reportingPeriod` code (documented: 1,2,3,4 = quarters, 6 =
  Mid-Year) + `reportingPeriodDescription`, share-class `description`, ADR block
  (`adrDescription`, `adrRatio`, `adrFsymId`, `adrTotalOutstanding`),
  `totalOutstanding` ("Number of shares outstanding as of `date`").
  `additionalProperties: false` (closed schema). Units of `totalOutstanding`
  are not stated (examples ~980.22 for FactSet ⇒ millions, INFERRED;
  `GP-UNRES-11`). The spec's own example pairs `reportingPeriod: 3` with
  description "2nd Quarter" (`GP-DISC-13`, spec-internal inconsistency).
- `/market-value`: **current-only** market value "in millions", currency
  reported per row; no history parameters at all. Not a substitute for
  historical market cap (which must be built from prices × shares, subject to
  the §4 basis caveats).

## 8. Response and error architecture

DOCUMENTED_OPENAPI:

- Success envelope everywhere: `{ "data": [ ... ] }`; calendar adds
  `meta.pagination`.
- **Three distinct error shapes** by endpoint family:
  1. Core (prices/returns/CA/market-value/batch-submission): `ErrorResponse`
     `{status, timestamp, path, message, subErrors{object, field, message,
     rejectedValue[]}}`.
  2. Shares outstanding: `SoErrorResponse` `{errors:[{id, code, links{about},
     title}]}`.
  3. Calendar: `ErrorResponseCalendar` `{errors:[{id, code, title, detail}]}`.
  Batch 404: `BatchErrorResponse` (nullable errors array).
  FS010's exception mapper must normalize all three (plus per-row inline errors,
  §6.6) into the project's typed error set.
- Documented 400 causes: date format, missing required parameter, **future
  date**, invalid/unknown parameter names ("spelling mistakes and use of
  improper casing"), malformed JSON, read timeout (>29s).
- 401: bad USERNAME-SERIAL / API key / outside key's IP range. 403: not entitled
  to endpoint or **id** ("User is not authorized for the **id**/endpoint
  requested") — per-id entitlement failures are possible, not just per-endpoint.
- 415: only `application/json` accepted.
