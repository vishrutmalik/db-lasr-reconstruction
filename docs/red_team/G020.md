## Verdict

**4 BLOCKING findings** (RT-G020-B1..B4), 11 non-blocking. The core as-of
semantics are solid — exact `<=` boundary is consistent across paths,
vintage selection matches an independent brute-force oracle at microsecond
boundaries, append-immutability holds, the membership backfill attack is
gated on every query path, and the D-015 recording teeth bite on the
sanctioned construction paths. The blocking findings are all on the edges
of the sanctioned path: the join kernel's naive-datetime guess, a
lag-config split-brain between query methods, an unguarded
adjusted-basis provider path, and the absence of any post-write integrity
verification of persisted artifacts.

None of the blocking findings is triggered by the current local-file
provider E2E fixture; each is demonstrated with the minimal adversarial
input below and each is reachable by a plausible future caller/config/
provider without any code smell at the call site. Per the charter
("assume it leaks until proven otherwise"), they block until fixed or
explicitly risk-accepted with a guard.

## BLOCKING findings

### RT-G020-B1 — `join_latest_known` silently localizes naive datetimes as UTC; future-knowledge rows join

`lasr.core.time_semantics.ensure_utc` rejects naive timestamps everywhere
("reject … rather than guessing a timezone"), and every `PitStore` path does
(probe A2). The one exception is the module whose docstring claims to own
the boundary rule "so no caller ever hand-rolls" it:
`join_latest_known` runs `pd.to_datetime(frame[col], utc=True)` on both
sides, which **localizes naive values as UTC instead of raising**. For a
caller whose decision timestamps are naive exchange-local times east of
UTC (Tokyo 15:00 JST = 06:00 UTC), the effective cutoff moves up to 9 hours
into the future, and rows whose knowledge_time is after the true decision
instant are joined. This is CI-001's master failure mode entering through
the sanctioned join kernel that G022+ feature builders are told to use.

Reproduction (value 42.0 is published 2h AFTER the true decision instant;
`knowable()` on the same input raises):

```python
from datetime import UTC, datetime
import pandas as pd
from lasr.data.point_in_time.asof_join import join_latest_known

# true decision instant: 2020-06-15 15:00 JST == 06:00 UTC
left = pd.DataFrame({"security_id": ["SEC-JP"],
                     "as_of": [datetime(2020, 6, 15, 15, 0)]})   # naive JST
right = pd.DataFrame({"security_id": ["SEC-JP"],
                      "knowledge_time": [datetime(2020, 6, 15, 8, 0, tzinfo=UTC)],
                      "value": [42.0]})                          # 2h in the future
j = join_latest_known(left, right, by=["security_id"], left_time="as_of")
assert j["value"].iloc[0] == 42.0   # future row joined — LEAK
```

Fix direction: assert tz-awareness of both time columns (mirror
`ensure_utc`) before `to_datetime`; a naive value must raise
`TimeSemanticsError`, not be guessed.

Severity note: the verifier's NB-4 flags the same surface as a
"convention inconsistency" (non-blocking). The reproduction above is why
this audit grades it BLOCKING: it is not merely inconsistent, it joins a
row whose knowledge_time is strictly after the true decision instant —
a demonstrated CI-001 violation through the one function callers are
directed to for boundary correctness, with no error and no warning.
Per the red-team charter (leak possible → BLOCKING), the finding is not
softened to match the verifier's grade.

### RT-G020-B2 — configured publication lags gate `as_of_frame` only; `universe()` and `classification()` ignore them

`PitQueryConfig.publication_lags` accepts a lag for ANY canonical table,
including `universe_membership_intervals` and `classification_intervals`.
`as_of_frame` honors it; `universe()` and `classification()` have no lag
parameter and never consult the config (`cutoff = ensure_utc(as_of)`),
so the same store+config answers the same PIT question two different ways.
The permissive path errs on the early-knowledge (leak) side. CI-005 says a
configured lag means the layer "never returns" rows inside
`(as_of − L, as_of]` — the interval-query paths do. The §11 interface stubs
share the gap (no lag on `universe`/`classification`), so this is a
layer-level finding (spec + implementation), not a deviation from spec.

Reproduction:

```python
from datetime import timedelta
from lasr.data.point_in_time.store import PitQueryConfig, PitStore
# store contains one membership row with knowledge_time KT (see probe file)
pit = PitStore(store, config=PitQueryConfig(
    publication_lags={"universe_membership_intervals": timedelta(days=90)}))
as_of = KT + timedelta(days=30)          # inside the embargo window
assert pit.as_of_frame("universe_membership_intervals", as_of).empty  # lag honored
assert pit.universe("U", as_of) == {"SEC-A"}                          # lag IGNORED
```

Full script: `probe_ac_boundary_lag.py` (section C2; classification shows
the identical split-brain). Fix direction: either thread
`_effective_lag` through `universe()`/`classification()`, or make
`PitQueryConfig` REJECT lag entries for tables served by non-lag-aware
paths so the config cannot promise what the API does not deliver.

### RT-G020-B3 — `corporate_action_basis=ADJUSTED` prices are stored as "unadjusted ground truth" and then double-adjusted: phantom +100.8% split-date return

The D-011 basis check asks only "is the basis KNOWN?". A provider that
declares `ADJUSTED` (a legal declaration; the synthetic provider declares
`UNADJUSTED`, a future API adapter can declare `ADJUSTED`) passes the check,
grades `RETRO_WINDOW`, and `build_prices_daily` copies its already-adjusted
closes into `prices_daily` — a table whose schema and
`canonical_schemas.md` §2 document as UNADJUSTED ground truth. No builder
consults `capability.corporate_action_basis` (grep: only `stamping.py`
reads it, for the downgrade record). `compute_adjustment_factors` then
derives split/dividend factors from `corporate_actions` — factors that are
only correct on top of unadjusted closes — and the FM-17 forbidden-column
guard cannot fire because the adjusted series arrives in the `close`
column, not as `adj_close`. End-to-end: the "adjusted" series shows a
+100.8% phantom return across a 2:1 split (correct: +0.4%), and the
dividend total-return factor is computed off a wrong (adjusted) ex-date
close. Zero warnings, zero downgrade events, nothing in the manifest.

Reproduction (`probe_f_actions.py` section F2, abridged):

```python
cap = FamilyCapability(available=True, supports_pit=False,
                       revision_support=RevisionSupport.LATEST_ONLY,
                       fields=frozenset({"close"}), notes="future API provider",
                       corporate_action_basis=CorporateActionBasis.ADJUSTED)
assert grade_dataset(FieldFamily.MARKET_DAILY, cap) is PitGrade.RETRO_WINDOW
# provider serves SPLIT-ADJUSTED closes: 100.0 -> 100.4 across a real 2:1 split
build = build_prices_daily(raw_adjusted_bars, ids, ctx_with(cap))   # accepted, no downgrade
factors = compute_adjustment_factors([split_2_for_1], canonical_prices)
# adjusted series: 100.0 -> 100.4 * 2.0 = 200.8  => +100.8% phantom return
```

Fix direction: the canonical build must reconcile the declared basis with
the `prices_daily` contract — refuse `ADJUSTED` market frames (or de-adjust
with provider factors) and/or record basis in the prices manifest and block
`build_adjustment_factors` when the price basis is not `UNADJUSTED`.
CI-049/LT-018 downstream cannot hold without this.

### RT-G020-B4 — persisted artifacts have no post-write integrity verification: payload retro-dating and D-015 record erasure are invisible to every shipped audit

The layer's guarantees ("datasets are content-addressed and immutable",
"later inserts never change earlier answers", D-015 recording is
"MANDATORY … audit-grade") are enforced at WRITE time only. Nothing —
not `read_records`, not `PitStore`, not `verify_manifest_payload` — ever
recomputes `content_hash` or `max_knowledge_time` against the parquet
payload, and the manifest itself is not covered by any hash. Three
demonstrated consequences (`probe_d_forgery.py`):

(a) **Payload retro-dating (leak).** Rewrite `part-*.parquet` with every
`knowledge_time` moved from the honest 2024 retrieval stamp back to the
bar close. `PitStore.as_of_frame` at a 2020 `as_of` goes from 0 rows to
serving the data; `verify_manifest_payload` reports **0 problems**. The
manifest's `content_hash` and `max_knowledge_time` both disagree with the
payload — the evidence of tampering is sitting on disk — but no shipped
code path ever checks either on read or audit.

(b) **D-015 record erasure (forgery).** Edit `manifest.json` of a
legitimately downgraded dataset: `pit_grade="RETRO_WINDOW"`,
`adjustment_basis_acknowledged=true`, `downgrade_events=[]`. This lands in
a LEGAL manifest state (the acknowledged-basis branch of the D-011 table),
so `read_manifest` and `verify_manifest_payload` both pass clean — the
mandatory downgrade record is destroyed post-hoc with no detectable trace.
Dataset ids are content-addressed over records only, so the manifest edit
does not perturb addressing.

(c) **Write-path forgery (deferred detection).** `CanonicalStore.write`
never re-validates the manifest model; a `model_construct(...)` manifest
with `pit_grade=RETRO_WINDOW` and no downgrade events persists successfully
(`created=True`). It is caught on a later `read_manifest` — but
`PitStore`'s data path (`read_records`) never reads manifests at all, so
the dataset remains fully queryable regardless. This sub-item is the
verifier's NB-2, independently found; they graded it non-blocking on the
grounds that "both catch nets work (`read_manifest` … ;
`verify_manifest_payload` flags the on-disk JSON), so there is no silent
path". Probes (a) and (b) above show that reasoning does not hold for the
finding class: BOTH catch nets pass clean (0 problems) against payload
retro-dating and against the legal-state manifest rewrite. (c) alone would
indeed be non-blocking; (a)+(b) are why the artifact-integrity gap as a
whole is BLOCKING.

This matters beyond a malicious-insider model: the artifact store in this
deployment lives on OneDrive-synced storage, where partial syncs, conflict
resolution, and file restores are realistic accidental mutation sources,
and the quality module's own docstring names on-disk "tampering or drift"
as its concern while auditing only manifest self-consistency. Given this
layer is the foundation every backtest's validity rests on, an
integrity-verification gap that a one-line rewrite defeats is blocking.

Fix direction (cheap): an `audit_dataset(store, table, dataset_id)` that
recomputes `content_digest` over the parts and re-derives
`max_knowledge_time`, wired into the G021 quality battery and optionally
into `PitStore._records`; have `store.write` round-trip the manifest
through `model_validate` before persisting; consider hashing the manifest
(sans hash) into the dataset directory to bind (b).

## NON-BLOCKING findings

- **RT-G020-N1 — per-call lag silently replaces (can zero) the configured
  lag.** `as_of_frame(table, as_of, lag=timedelta(0))` returns rows inside
  a configured 90-day embargo (probe C1). Documented as "applied by
  default", but CI-005's "never returns" is defeated by a plausible caller
  who believes `lag=0` means "no EXTRA lag". Recommend
  `max(configured, requested)` or an explicit `override_configured_lag`
  flag.
- **RT-G020-N2 — `universe()` defaults to NOT applying the CI-003 exclusion
  side.** `listing_table=None` is the default, so a delisted-before-`as_of`
  security with an open vendor interval stays in the universe (probe E4).
  The direction is anti-survivorship (dead names stay IN), so it is not a
  bias leak, but CI-003's exclusion clause only holds if every caller
  remembers the optional argument — a permissive default on the checklist
  (#8). Recommend making the listing intersection explicit-or-required.
- **RT-G020-N3 — order-dependent snapshot ids on raw sort-key ties.**
  `raw_fundamentals` sorts by `(ticker, exchange, metric, period_end)` but
  its PK uses `fiscal_period`; two rows tying on the sort key (Q4 + FY
  ending the same date) pass U4 in either order and hash to two different
  `snapshot_id`s for the same row set (probe G2) — spurious duplicate
  snapshots, MP §15 idempotency broken on ties, CI-043 substrate. Also
  noted: an identically-contented drop re-ingested in shuffled order is a
  hard `IntegrityError` (fail-loud, acceptable, but LT-020(b) order
  invariance then rests on providers emitting sorted frames). Fix: make
  every raw sort key a PK superset (append the PK columns), as the
  canonical schemas already do.
- **RT-G020-N4 — partial-write wedge.** A crash after `part-*.parquet` but
  before `manifest.json` leaves a directory that can never be completed:
  the retry hits `directory.exists()` → `read_manifest` → `StoreError`
  forever (probe G3). Write to a temp dir + atomic rename, or treat a
  manifest-less directory as absent-and-removable.
- **RT-G020-N5 — silent empties on identifier typos.** Unknown
  `universe_id` → `frozenset()`; unknown `scheme` → `{}`; a typo'd
  key-filter column in `as_of_frame(keys=...)` matches nothing silently
  (probe H1). This is the "empty frame to signal absence" pattern the
  provider contract §3 forbids, one layer up. Also: unknown table raises
  bare `KeyError` from the registry rather than `PitQueryError` (=
  verifier NB-3).
- **RT-G020-N6 — empty datasets skip the `max_knowledge_time` cross-check.**
  `_check_max_knowledge_time` is guarded by `if records and …`, so a
  zero-row dataset persists any nonsense `max_knowledge_time` (probe H2;
  = verifier NB-5).
- **RT-G020-N7 — malformed knowledge values silently dropped.** All PIT
  query paths skip rows whose knowledge cell is not a `datetime`
  (`isinstance` guard) instead of raising; exclusion is leak-safe but
  silent (MP §26). Reachable only with hand-built records today.
- **RT-G020-N8 — no deletion/tombstone representation for vintaged
  tables.** A vendor deleting an observation cannot be represented;
  `assemble_vintages` treats absence as no-op, so the stale statement stays
  the latest vintage forever, silently. Design note for the vintage model
  (LT-010 family) — needs a documented position before real restatement
  feeds arrive.
- **RT-G020-N9 — naive `bar_close_time`/`StampingConfig` times are
  interpreted as UTC** (documented). A config typo writing NY close as
  naive `16:00` stamps bars 4–5h EARLY — an intraday-scale leak surface
  that only materializes for intraday `as_of` grids. Recommend requiring
  tz-aware close times in config (the DST probe A4 shows tz-aware handling
  is already correct).
- **RT-G020-N10 — representability gaps.** (i) `raw_corporate_actions` PK
  `(ticker, exchange, action_type, effective_date)` cannot hold two
  same-type same-day actions (LT-018's "special and regular cash
  dividends" on one ex-date) — ingestion fail-louds, but the scenario is
  unrepresentable; canonical `action_id` minting already disambiguates via
  `provider_action_id`, so only the raw PK blocks. (ii) canonical
  `fundamentals` event key `(security_id, metric, fiscal_period)` omits
  `period_end`; a fiscal-year-end change producing two periods that
  normalize to the same `FY<year>` label chains them as restatements of
  one event instead of two events.
- **RT-G020-N11 — knowledge honesty rests on caller-supplied
  `retrieval_time`** (the no-wall-clock design, MP §26). Correct for
  testability, but nothing cross-checks that an ingestion CLI passes a
  truthful retrieval time; recommend a G021 ingestion-side sanity check
  (retrieval_time vs payload mtimes / monotonicity per provider).
