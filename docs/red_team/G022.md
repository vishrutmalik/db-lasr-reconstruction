## Verdict

**1 BLOCKING finding** (RT-G022-B1), 8 non-blocking. The core as-of
discipline of the feature layer is solid: forward context reads are
refused (including timezone-disguised ones), the CI-001 boundary is exact,
declared-source enforcement holds against straightforward smuggling,
frames are not views into store state, the three re-derived library
formulas are bit-exact against independent recomputation with correct
skip-window / restatement-vintage / trailing-vintage behavior, transforms
carry no cross-date state, and the full library run is bit-identical
across `PYTHONHASHSEED` values. The blocking finding is on the stamping
edge: the stored `FeatureValueRow.knowledge_time` ignores the PIT layer's
configured floor lags, so under any config where a floor exceeds the
registry lag the stamp claims knowability at an instant when the same
`PitStore` refuses to serve the inputs. Inert under the default (no-floor)
config — but floors are the designed A-002/RT-G020-N1 mechanism, so per
the charter it blocks until fixed or explicitly risk-accepted.

## BLOCKING findings

### RT-G022-B1 — Stored `knowledge_time` understates availability when a PIT floor lag exceeds the registry lag

`FeatureContext._record_knowledge` stamps rows with
`input knowledge_time + the context's OWN applied lag`
(`spec.publication_lag` for vintaged tables, 0 for bar tables), while the
`PitStore` gates the same query at
`effective = max(configured_floor, requested)` (RT-G020-N1). The context
never learns the store's effective lag — `computation.py` line 177 even
converts a zero lag to `lag=None`, delegating gating to the floor while
recording `+0`. Whenever `PitQueryConfig.publication_lags[table] >
spec.publication_lag` (which includes EVERY price-table feature, spec lag
0, under any configured price floor), the stored
`FeatureValueRow.knowledge_time` is EARLIER than the instant at which the
row's inputs were actually knowable under the run's own configuration.
That is precisely the "stamp earlier than an input it actually used" leak
class: a downstream consumer (G023 training-example builder, CI-006
horizon checks) that gates on the stored stamp will treat the feature as
available up to `floor − spec_lag` too early.

Values are NOT contaminated (gating itself is correct — probe B3 confirmed
the in-floor bar is invisible); the defect is confined to the stamp, and
it is inert under the default empty `PitQueryConfig`. It blocks because
floors are the designed A-002 config mechanism (G033 will configure the
3-month fundamental lag; any mismatch where config > spec silently
produces optimistic stamps) and because the engine's own CI-001 assertion
(`max_kt <= as_of`) cannot catch it — the stamp errs EARLY, not late.

Reproduction (venv `~/.venvs/lasr-redteam-g022`, from the worktree root;
uses the unit-suite fixture helpers):

```python
import sys, tempfile
from datetime import UTC, date, datetime, timedelta
from pathlib import Path
sys.path.insert(0, "tests/unit")
from test_features_fixtures import AS_OF, price_bar, write_table
from test_features_registry import toy_spec
from lasr.data.canonical.store import CanonicalStore
from lasr.data.point_in_time import PitQueryConfig, PitStore
from lasr.features.computation import RawObservation
from lasr.features.engine import FeatureEngine
from lasr.features.registry import FeatureRegistry

def kernel(ctx, securities):
    f = ctx.frame("prices_daily", keys={"security_id": securities})
    r = f.to_dict("records")[-1]
    d = r["event_date"]
    return {str(r["security_id"]): RawObservation(
        value=float(r["close"]),
        observation_time=datetime(d.year, d.month, d.day, tzinfo=UTC))}

store = CanonicalStore(Path(tempfile.mkdtemp()))
ref = write_table(store, "prices_daily",
                  [price_bar("SEC-A", date(2021, 12, 20), close=100.0)])
pit = PitStore(store, dataset_ids={"prices_daily": ref.dataset_id},
               config=PitQueryConfig(
                   publication_lags={"prices_daily": timedelta(days=5)}))
registry = FeatureRegistry(); registry.register(toy_spec(), kernel)
(row,) = FeatureEngine(registry, pit).compute(
    "toy_close", 1, AS_OF, ["SEC-A"]).rows
print(row.knowledge_time)   # 2021-12-20 21:00 (raw bar kt, floor ignored)
print(len(pit.as_of_frame("prices_daily", row.knowledge_time)))  # 0 (!)
# the stamp claims knowability at an instant when the SAME store serves
# zero rows; effective availability was kt + 5d = 2021-12-25 21:00.
```

Vintaged variant (fundamentals floor 120d, spec lag 90d → stamp kt+90d,
availability kt+120d) reproduced identically in probe B4.

Suggested direction (implementer's choice): the context must record
`kt + effective_lag`; today it cannot know the floor — expose the
effective lag on the PIT surface (e.g. a public
`PitStore.effective_lag(table, lag)` or return it alongside
`as_of_frame`) and have `_record_knowledge` use it. Alternatively assert
at engine construction that no configured floor exceeds the registry lag
of any registered feature touching that table (fail-loud config guard).

## Non-blocking findings

### RT-G022-N1 — Metric-filter validation/matching asymmetry defeats the declared-metric guard

`_require_declared_metric_filter` validates `str(metric)`; the PIT store's
`_matches` then compares with `record != expected`, i.e. the CALLER
object's `__eq__`. A key object with `str() == "BOOK_VALUE"` but
`__eq__` matching `"TOT_ASSET"` passes validation and is served the
undeclared metric's rows (probe A5b: kernel declared only BOOK_VALUE, read
TOT_ASSET values). No time-travel — rows remain knowledge-gated — but the
MP §18 "refuses undeclared metric ids" guarantee is bypassable from the
public API by first-party kernel code, which is the exact threat model the
guard exists for. Fix: after validation, rewrite the outgoing key filter
with the validated `str` values (`keys = {**keys, "metric": requested}`).

```python
class Sneaky:
    def __str__(self): return "BOOK_VALUE"
    def __eq__(self, other): return other == "TOT_ASSET"
    def __hash__(self): return hash("TOT_ASSET")
# ctx.frame("fundamentals", keys={"security_id": s, "metric": Sneaky()})
# -> serves TOT_ASSET rows to a BOOK_VALUE-only feature
```

### RT-G022-N2 — Undeclared-column dropping skipped for metric tables; post-as_of `ingestion_time` exposed

`FeatureContext.frame` applies `_visible_columns` only to column-shaped
tables. Metric-namespaced frames arrive with ALL schema columns:
`report_date`, `knowledge_basis`, `unit`, `currency`, and notably
`ingestion_time`, which in the fixtures (and in any retrieval-stamped real
dataset) is a wall-clock timestamp AFTER `as_of` (probe A8:
`2022-06-30 12:00` visible at as_of `2021-12-31 12:00`). Constant per
dataset, so cross-sectional signal is nil, but (a) the module docstring
overclaims ("drops undeclared columns from returned frames"), and (b) a
kernel consuming `ingestion_time` would silently change values whenever
data is re-ingested — a reproducibility hazard. Fix: restrict metric-table
frames to plumbing + `value` (and document `period_end`/`fiscal_period` as
plumbing), or amend the docstring and add a spec note.

### RT-G022-N3 — `SourceFieldCatalog.metric_ids` is mutable in place

The frozen dataclass holds a plain `dict` (`default_factory=lambda:
dict(DEFAULT_METRIC_IDS)`). Probe A6: assigning
`registry.catalog.metric_ids["fundamentals"] = frozenset({...,
"SECRET_METRIC"})` succeeds and a feature over the never-declared metric
then registers cleanly — the sanctioned `with_metrics` copy-on-extend path
is bypassable. First-party misuse only, but one line fixes it (wrap in
`types.MappingProxyType` in `__post_init__`, with frozenset values it
becomes deeply immutable).

### RT-G022-N4 — `registry_hash` is kernel-blind

Two registries with identical specs and lists but DIFFERENT compute
kernels hash identically (probe F4). The hash is documented as covering
"registry content (specs + lists)", and hashing code objects portably is
genuinely hard — but the consequence is that implementation drift under an
unchanged formula string is invisible to lineage, which is the failure MP
§18's "a changed formula is a NEW version" discipline is supposed to
catch. Recommend registering this as an explicit assumption/limitation
(A-G022 family) and noting that the guard is the hand-computable fixture
suite (a changed kernel that changes any value breaks a pinned fixture).

### RT-G022-N5 — No structural lag floor for statement-like tables at the registry level

`FeatureSpec` accepts `publication_lag=0` on vintaged tables;
`eps_revision_3m` ships that way on `estimates_consensus` (defensible —
the vintage `knowledge_time` IS the revision timestamp), and probe A7
shows a lag-0 fundamentals feature would see statements 90d fresher than
the library's value features. CI-005's text binds CONFIGURED lags, so this
is legal; the protection against a mis-registered lag-0 fundamentals
feature is spec review plus `PitQueryConfig` floors — and per RT-G022-B1
the floor path currently mis-stamps. Recommend: when G033 configures the
paper lags, add an assertion that every registered feature on a lagged
family carries `spec.publication_lag >= configured floor` (which also
neutralizes B1 for that config).

### RT-G022-N6 — `date` as `as_of` fails untyped

`ensure_utc(date(...))` raises `AttributeError: 'datetime.date' object has
no attribute 'tzinfo'` (probe A3) rather than `TimeSemanticsError`. Fails
loudly (safe) but violates the typed-error discipline (RT-G020-N5 family).
One `isinstance(value, datetime)` check in `ensure_utc` fixes it repo-wide
(note: `date` must be tested via `not isinstance(value, datetime)` since
`datetime` subclasses `date`).

### RT-G022-N7 — `min_coverage = 0.0` makes an EMPTY cross-section eligible

`eligible = coverage >= spec.min_coverage` with zero rows and
`min_coverage=0.0` yields `eligible=True, rows=()` (probe E3). The spec
range [0, 1] permits it; the library uses 0.5 throughout. An
empty-but-eligible result is a silent-empty flavor for a consumer that
branches on `eligible` alone. Consider `eligible = kept > 0 and coverage
>= min_coverage`, or a registry refusal of `min_coverage == 0`.

### RT-G022-N8 — A-G022-01 stamp is universe-dependent; persistence collision risk (observation for G023)

Probes B1/B2: the same `(feature_id, version, security_id,
observation_time)` row is stamped `2021-12-30 21:00` when computed jointly
with a fresh security and `2021-12-21 21:00` when computed alone — values
identical, stamps differ. Direction verified honest (never earlier than
the row's own inputs; keeper pins it). But `feature_values`' primary key
EXCLUDES `knowledge_time`, so persisting the same logical cross-section
computed over two universes produces PK-identical rows with conflicting
stamps. Downstream storage/joins (G023) must treat the stamp as a
cross-sectional property of the computation batch, never as per-security
truth — worth an explicit line in the A-G022-01 register entry.

## Positive results worth recording

- CI-001 boundary is exact and consistent through the context (`<=` at the
  instant, refused at +1µs even disguised in a non-UTC offset).
- The three re-derived formulas are bit-exact against independent
  recomputation over 400 days of seeded bars; the 12-1 skip window has
  teeth in BOTH directions (jump inside → 0.0; at the −30d boundary →
  included); volatility is ddof=1 daily with no hidden annualization;
  asset growth follows the knowable vintage through the 90d lag in both
  restatement directions; eps_revision's trailing leg is the
  vintage-as-of-then, not the latest.
- Transforms: no cross-call state; frozen winsorizer bounds survive
  cross-date application bit-identically; adversarial float ties are
  deterministic under both tie rules across 40 shuffled runs.
- Full-library digests (values, stamps, coverage, registry hash) are
  identical across three `PYTHONHASHSEED` values in separate processes.
- Coverage arithmetic is honest for ±inf/NaN; NaN prices cannot enter at
  the canonical layer (`gt=0` rejects NaN).
- Hash: registration-order independent, list-order sensitive, immune to
  the delimiter-injection and field-swap collision attempts.
